# Пульт МИ: дашборд координатора массовых инцидентов

Один экран, на котором координатор сразу видит четыре группы инцидентов из ITSM, не пропускает критические
и быстро передаёт назначенные на координаторов инциденты в профильные команды.

ITSM для нас чёрный ящик, её эмулирует файл `data/incidents.json` (формат как в `character_problems.json`).
Сервер следит за файлом и по WebSocket рассылает актуальное состояние, дашборд перерисовывается сам.

## Запуск

Нужен Node.js 20+.

```bash
npm install
npm run dev          # сервер :3001 + интерфейс http://localhost:5173
```

Для показа без режима разработки:

```bash
npm run build
npm start            # всё на http://localhost:3001
```

Перед демонстрацией выполните `npm run seed`: даты из выгрузки (8–10 ноября) сдвинутся к текущему времени,
и сроки на экране станут живыми. При первом запуске это происходит автоматически.

## Что на экране

| Группа | Правило | Зачем |
|---|---|---|
| Критические | `priorityId = 4` (только «Наивысший»). Решённые остаются ещё 12 часов зелёными со штампом «Решён» | Их нельзя пропустить |
| На координаторах | `assignedGroupName = «КЦ ИТ Координаторы Массовых Инцидентов»`, статус не «Закрыт» | Быстро передать в другую команду |
| Высокий приоритет | `priorityId = 3`, статус «Назначен» или «Выполняется» | Каждый может перерасти в критический |
| Исследование ситуации | `stateId = 20` | Решён, идёт разбор причин. Может прийти на координаторов |

Один инцидент может быть в нескольких группах сразу. На карточке это видно по меткам других групп.

На каждой карточке: продукт и сервис, когда возник, кто решает (группа и исполнитель), статус, обратный отсчёт до срока,
заявитель и канал, число писем. Полоса слева убывает по мере приближения срока: зелёная, жёлтая при угрозе, красная штриховка при просрочке.

Ниже доски строка «Решены, но не закрыты» (статус «Завершен»): к ним могут вернуться.
Справа лента изменений из ITSM и почта по инцидентам.

### Как координатор узнаёт о событиях

- **Новый критический.** Полноэкранная красная тревога с сиреной, которая повторяется, пока координатор не нажмёт
  «Принял, беру на контроль». Плюс постоянная красная полоса над доской, мигающий заголовок вкладки и системное уведомление,
  если окно свёрнуто. Подтверждение хранится на сервере, видно всем («на контроле: Дядя Фёдор»), и после перезагрузки страницы тревога не теряется.
- **Критический решён.** Карточка становится зелёной со штампом «Решён», зелёное уведомление и восходящий сигнал.
- **Назначен на координаторов.** Фиолетовое уведомление со звуком, карточка поднимается наверх с рамкой и кнопкой «Принял».
  Кнопка «Передать в команду» прямо на карточке: выбор команды, и инцидент уходит из группы.
- **Любое изменение** (статус, срок, приоритет, команда) подсвечивает карточку вспышкой и попадает в ленту изменений.

### Прочее

- Поиск, фильтры по продукту и типу влияния, «только со сроком под угрозой». Фильтры никогда не прячут критические.
- Прогноз нарушения срока: если до срока осталось меньше, чем обычно уходит на решение инцидента такого приоритета
  (медиана по истории в той же выгрузке), или инцидент до сих пор не взят в работу, а половина срока прошла.
- Клик по карточке открывает муляж ITSM (`/itsm/INC...`) в одной и той же вкладке: все атрибуты, переписка, история изменений
  и действия (передать, сменить статус, приоритет, срок, решить). Действия уходят POST-запросом и меняют JSON.
- Почта: `data/mail.json`, письма привязаны к инцидентам по номеру. Важные письма (алерты мониторинга) дают уведомление.
- Если файл с данными временно невалиден (правят руками), на экране предупреждение, показываются последние корректные данные.
- Потеря связи с сервером видна в шапке, клиент переподключается сам, а пока опрашивает API раз в 5 секунд.

## Сценарий защиты

1. `npm run seed`, затем `npm run dev`, открыть http://localhost:5173 и нажать «Начать смену со звуком».
2. Открыть `data/incidents.json` в редакторе, у любого активного инцидента (`"stateId": 0` или `2`) поставить `"priorityId": 4`
   и сохранить. Через долю секунды на экране тревога и сирена. Текстовые поля (`priority`, `state`) менять не обязательно.
3. Нажать «Принял». Красная полоса остаётся, пока инцидент не решён.
4. В редакторе поменять у него `"stateId"` на `7`. Карточка зеленеет, приходит уведомление «Критический инцидент решён».
5. У другого инцидента поменять `"assignedGroupName"` на `"КЦ ИТ Координаторы Массовых Инцидентов"`. Уведомление и звук,
   карточка в группе «На координаторах». Нажать «Передать в команду» и выбрать команду: инцидент уходит из группы.
6. Поменять `deadline` или `priority`: карточка подсвечивается, отсчёт пересчитывается, событие в ленте.

То же без редактора: кнопка «Имитация ITSM» в правом верхнем углу (или `?demo` в адресе) или симулятор в отдельном терминале:

```bash
npm run simulate              # случайные изменения каждые 6 секунд
npm run simulate -- 3         # каждые 3 секунды
npm run simulate -- newCritical
npm run simulate -- list      # все сценарии
```

## Как устроено

```
 data/incidents.json ──fs.watch + опрос mtime──▶ server/index.js ──WebSocket /ws──▶ React Query cache ──▶ экран
 data/mail.json                                  │ сравнивает снимки, формирует события
                                                 │ хранит подтверждения (data/dashboard-state.json)
 муляж ITSM, кнопки ──POST /api/incidents/:id───▶│ меняет JSON так же, как ITSM
```

- `server/index.js`: Express + ws. API: `GET /api/state`, `POST /api/incidents/:id`, `POST /api/ack`, `POST /api/demo/:scenario`.
- `server/events.js`: разница между снимками превращается в события (новый критический, решён, назначен на координаторов и т. д.).
- `server/scenarios.js`, `server/simulate.js`: сценарии изменений для демонстрации.
- `server/seed.js`: готовит рабочий файл из `data/source/character_problems.json` (исходник не меняется).
- `src/lib/model.ts`: правила групп, сроки, прогноз. `src/Dashboard.tsx`: экран. `src/itsm/`: муляж ITSM.
- Стек: React 19, TypeScript, Vite, TanStack React Query, GSAP (Flip для перестановки карточек, тревога, вспышки), Express, ws.
  Звуки генерируются Web Audio, шрифты Golos Text и Unbounded лежат локально, интернет на защите не нужен.

### Замечания по данным

- В `incidents_attributes.json` написано «7 — Закрыт, 10 — Завершен», а в самих данных наоборот:
  `7 = Завершен (Resolved)`, `10 = Закрыт (Closed)`, плюс `20 = Исследование ситуации (Research)`. Ориентируемся на данные.
- В исходной выгрузке нет инцидентов с приоритетом 4. Критические появляются через симулятор или правку файла.
- «Решён, но не закрыт» — это статус 7: проблема устранена, но к инциденту могут вернуться.

### Что можно развить

- Настоящая интеграция почты: сервер читает ящик по IMAP или через Exchange и пишет письма в тот же `mail.json`.
- Вместо файла опрашивать API ITSM: достаточно заменить чтение файла в `server/index.js`, остальное не меняется.
- Эскалация: если критический не подтверждён за N минут, писать старшему смены.
